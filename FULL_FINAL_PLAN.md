## Phase 1: Core Bug Fixes & Financial Accuracy

> **Priority: CRITICAL — Execute first. All financial data depends on this.**

### 1.1 Supplier/Client Debt Sync Bug

* **Issue:** Advance payments (overpayments) were ignored by a flawed `max(0, ...)` logic when receiving orders, causing the database `debt_amount` to drift from the actual ledger.
* **Fix:** Remove all manual addition/subtraction logic from `PurchaseOrderController` and `SalesController`. Force the system to call `$supplier->recalculateDebt()` and `$client->recalculateDebt()` immediately after *any* order creation, update, cancellation, or payment. This guarantees the DB column and the mathematical ledger are permanently synced.
* **Verification:** After fix, manually create a PO, partially pay it, overpay it, then cancel it — the `debt_amount` column must match the ledger sum at every step.

### 1.2 Supplier Deposit Not Reflected in Accounts Page (Financial Bug)

* **Issue:** When a standalone advance payment (deposit) is paid to a supplier with no linked purchase order, the Suppliers page correctly shows it as a credit. However, the Accounts page financial summary does **not** subtract these deposits from total supplier liabilities, causing the displayed total debt figure to be inflated.
* **Root Cause:** The Accounts page query calculates supplier liabilities from purchase order balances only. It ignores the `supplier_payments` (or equivalent) table rows that have no `purchase_order_id`.
* **Fix:** Update the Accounts page backend query (likely in `AccountController` or equivalent) to include standalone supplier deposits — payments with no linked PO — and subtract them from the total supplier liability figure. The formula must be: `Total Supplier Liability = Sum of PO balances - Sum of standalone advance deposits`.
* **Verification:** Pay a deposit to a supplier with no PO. Confirm the Accounts page total supplier debt decreases by exactly that amount immediately.

### 1.3 Production Order Storage Filter

* **Modification:** Update `InventoryController::getProducts` to calculate and return a dedicated `stock_wshp` variable (Stock in WSH-P).
* **Frontend:** Update `ProductionOrderForm.jsx` so the maximum allowed quantity and the displayed available stock rely exclusively on `stock_wshp` instead of the global total.
* **Verification:** Ensure a product with stock in WSH-M but zero in WSH-P shows 0 available in the production form.

### 1.4 Used Materials in Production PDF

* **Backend:** Ensure the backend eager-loads `operationProducts.product.materials`.
* **Frontend:** Add a new column `"الخامات المستخدمة"` (Used Materials) to the PDF generated by `ProductionOrderCard.jsx`. It will multiply product quantity by BOM requirements, or display `-` if no materials are used.
* **Verification:** Generate a PDF for a production order containing products with and without BOMs. Confirm correct multiplication and `-` fallback.

## Phase 2: New Feature — Wasted Materials Management (هالك التصنيع)

> **Depends on:** Phase 1.3 (WSH-P stock logic must be correct before waste deductions are added.)

### 2.1 Virtual Waste Storage & Logging

* **Storage:** Ensure `WSH-WASTE` (مخزن الهالك) exists in the database as a standard warehouse. Use a database seeder or migration check — never assume it exists manually.
* **Logging:** Add an optional `"تسجيل هالك المواد"` section in the Complete Production (إنهاء التشغيل) popup.
* **Movements:** When logged, the backend creates a `Production_Waste` movement (deducting from `WSH-M`) and a `Waste_Receipt` movement (adding to `WSH-WASTE`). Both movements must be wrapped in a single `DB::transaction()`.
* **Validation (critical):** Before creating the waste movement, the backend must verify that the logged waste quantity does **not** exceed the available stock in `WSH-M`. If it does, return a `422` validation error with a clear Arabic message. Never allow a negative stock state.

### 2.2 Waste Analytics & Operations

* **Analytics:** Users can filter the Inventory page by `WSH-WASTE` to view exact quantities and total financial losses of wasted materials.
* **Recycling (Quick Transfer):** Unlock the `"نقل سريع"` (Quick Transfer) button for Materials inside `warehouses/page.jsx`. This allows users to transfer usable scrap materials from `WSH-WASTE` back to `WSH-M`.
* **Selling Scrap:** Update `SalesController` and the Sales Invoice frontend form to support selling both `"Products"` and `"Materials"` as line items. This allows selling scrap directly from `WSH-WASTE` to a client, generating revenue and removing it from waste stock. Stock deduction must pull from the selected warehouse (`WSH-WASTE`), not the global total.

## Phase 4: Implementation & Verification Guardrails

> **These rules apply to every phase without exception.**

### 4.1 Database Safety

* Wrap all multi-table write operations in `DB::transaction()`. A failure in any single step must roll back the entire operation.
* Use `lockForUpdate()` on supplier/client and stock rows during PO receipts, payments, and stock deductions to prevent race conditions from double-clicks or concurrent requests.
* Never allow stock to go below zero. Every stock deduction must be preceded by a backend availability check inside the same transaction.

### 4.2 Rollback & Deployment Safety

* Before executing any migration on production, take a full database backup.
* Every migration must be reversible — write a `down()` method for every `up()`.
* Deploy backend changes before frontend changes. The frontend must never reference an API endpoint that does not yet exist.

### 4.3 Testing Requirements

* All 41 existing backend tests and 45 existing frontend tests must pass with zero regressions after every phase.
* New backend tests must be written for: debt recalculation after PO events, standalone deposit reflection in Accounts, waste quantity validation (over-limit rejection), and scrap sales stock deduction from correct warehouse.
* New frontend tests must be written for: `SearchableSelect` onChange firing on re-selection, and waste logging form validation.
* Manual verification paths before marking any phase complete:
  - PO receipt → debt sync check
  - Standalone deposit → Accounts page balance check
  - Production completion with waste logging → WSH-M deducted, WSH-WASTE credited
  - Scrap sale from WSH-WASTE → stock correctly removed, revenue recorded
  - Debt modal scroll on a small viewport
  - WhatsApp button generates a valid `wa.me` URL

### 4.4 Financial Data Integrity Rules (Permanent)

> These are non-negotiable rules that must never be broken in any future development:

1. **Never manually mutate `debt_amount`.** Always call `recalculateDebt()` and let it derive the value from the full transaction ledger.
2. **Never calculate financial summaries from a single table.** Accounts totals must always join all relevant payment and order tables to produce a complete picture.
3. **Never allow a partial transaction.** If stock moves out of one warehouse, it must atomically move into another within the same `DB::transaction()`.
4. **Never hard-delete financial records.** Orders, payments, and movements must be soft-deleted only, preserving the audit trail.
